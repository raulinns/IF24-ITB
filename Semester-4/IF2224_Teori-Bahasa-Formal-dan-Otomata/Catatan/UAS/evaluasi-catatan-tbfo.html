§4 Compiler — Error Handling tidak ada sebagai bagian mandiri
Gap kritisBelum Ada

Outline memasukkan Error Handling sebagai subbagian tersendiri dalam Compiler (§4.8), terpisah dari LL(1). Catatan saat ini hanya memiliki error handling di §10.2.9–10.2.10 (LL(1) section), sehingga konteks error handling sebagai komponen global compiler tidak ada. Poin-poin yang sepenuhnya hilang: (a) "reaksi yang dilarang" — compiler crash, infinite loop, atau target code rusak sebagai prinsip perancangan; (b) ad-hoc recovery; (c) dummy identifier sebagai teknik context-sensitive repair untuk identifier yang tidak dideklarasikan. Tanpa bagian ini, pembaca tidak memiliki gambaran bahwa error handling adalah komponen pipeline, bukan hanya fitur parser.

Yang perlu ditambahkan: paragraf 3–5 kalimat yang menjelaskan kontrak error handling compiler (lapor lokasi, lanjutkan parsing jika mungkin, jangan crash), lalu tabel singkat 5 strategi (panic mode, unit deletion, terminal repair, context-sensitive, spelling repair) dalam konteks compiler umum. Dummy identifier perlu satu contoh konkret: jika identifier x tidak dideklarasikan, compiler memasukkan x ke symbol table dengan tipe dummy agar analisis semantik lanjutan tidak cascade error.

§4 Compiler — Code Generation: instruction selection, register allocation, peephole hilang
Gap kritisBelum Ada

Bagian Code Generation catatan hanya membahas basic block, flow graph (§8.2.19), dan register/address descriptor (§8.2.20). Empat poin outline yang hilang: (a) instruction selection — cara memilih instruksi target dari pola IR; (b) evaluation order — urutan evaluasi ekspresi untuk meminimasi penggunaan register; (c) graph coloring untuk register allocation — teknik memecah konflik penggunaan register sebagai masalah pewarnaan graf; (d) peephole optimization — optimasi lokal pasca code generation dengan melihat jendela instruksi sempit untuk menghapus redudansi seperti mov r0, r0 atau tumpukan load/store berurutan.

Yang perlu ditambahkan: (1) satu paragraf tentang instruction selection sebagai pemetaan pola IR ke instruksi target; (2) definisi singkat graph coloring — "register allocation as graph coloring: buat interference graph, warnai dengan k warna (jumlah register), spill variabel tanpa warna"; (3) definisi peephole optimization dengan 2–3 contoh pola eliminasi umum.

§3 Mesin Turing — Trace eksekusi TM pada input konkret tidak ada
Gap kritisBelum Ada

Outline secara eksplisit menyebut "Trace eksekusi, termasuk contoh UAS seperti pengenal {0^n 1^n}" sebagai poin tersendiri. Ini sinyal kuat bahwa soal UAS dapat berupa "tunjukkan trace TM berikut pada input 0011" atau "rancang TM untuk bahasa X, tunjukkan langkah pada input tertentu." Catatan memiliki definisi ID dan aturan gerak yang baik, tetapi tidak ada contoh trace aktual step-by-step.

Yang perlu ditambahkan: trace tabel 4–5 kolom (state, tape content, head position, move, aksi) untuk TM pengenal {0^n 1^n} pada input 0011. Ini tidak membutuhkan penjelasan panjang — cukup tabel yang dapat diikuti sebagai template pengerjaan soal.

§3 Mesin Turing — Teorema komplemen RE hilang
Gap sedangBelum Ada

Outline §3.4.3 menyatakan: "Jika L RE dan komplemennya juga RE, maka L recursive." Ini teorema standar yang sering muncul dalam soal undecidability untuk membuktikan bahwa suatu bahasa bukan recursive (dengan menunjukkan komplemennya bukan RE). Catatan punya perbedaan RE/recursive yang baik di §7.2.11, tetapi tidak menyatakan teorema ini.

Yang perlu ditambahkan: satu paragraf + rumus: "Jika L ∈ RE dan L̄ ∈ RE, maka L ∈ Recursive. Kontraposisinya: jika L ∈ RE tetapi L ∉ Recursive, maka L̄ ∉ RE." Ini langsung berguna untuk analisis Ld dan Lu.

§3 Mesin Turing — Transducer untuk fungsi integer (representasi unary) tidak ada
Gap sedangSebagian

Catatan §7.2.9 membahas transducer secara umum tetapi tidak menyebutkan representasi unary untuk integer. Outline menekankan "input integer direpresentasikan unary" dan "relevansi UAS: desain TM untuk f(n)=2n" sebagai poin eksplisit. Tanpa ini, mahasiswa tidak tahu format encoding yang dipakai saat soal meminta desain TM komputasi.

Yang perlu ditambahkan: kalimat "Integer n biasanya direpresentasikan sebagai n buah simbol 0 atau 1 (unary), misalnya n=3 ditulis 000" plus contoh singkat pola TM untuk f(n)=2n: scan input, untuk setiap 0 input tulis 00 pada output tape, dsb.

§2 CYK — Kompleksitas konversi CNF per tahap tidak ada
Gap sedangBelum Ada

Outline §2.1.5 menyebutkan tiga angka kompleksitas spesifik: generating/reachable cleanup = linear; unit-pair computation = O(n²); ukuran grammar hasil CNF = O(n²). Catatan hanya menyebutkan "grammar dapat membesar" secara umum di Komentar 6.2 tanpa angka. Jika soal menanyakan kompleksitas preprocessing CNF (bukan kompleksitas CYK itu sendiri), catatan tidak memberikan jawaban.

§7 IR — Postfix notation tidak punya subsection sendiri
Gap sedangTerlalu Dangkal

Postfix adalah bentuk IR yang paling sering muncul dalam soal UAS berupa "baca eksekusi stack" atau "ubah ekspresi ke postfix." Catatan menyebutkan BZ/BR di §11.2.8 dan menghubungkan ke "kaitan soal UAS" di §11.2.10, tetapi tidak punya penjelasan lengkap: apa itu postfix, bagaimana mengkonversi ekspresi aritmetika ke postfix, bagaimana control flow diwakili dengan BZ/BR. Catatan §12.2.12 menyebutkan "stack-based VM sejalan dengan postfix" tetapi penjelasan sistematis tidak ada.

Yang perlu ditambahkan: subsection kecil (setengah halaman) dengan: (1) definisi postfix; (2) konversi contoh a + b*c; (3) BZ (branch if zero/false) dan BR (branch) untuk if/while; (4) contoh trace evaluasi stack.

§7 IR — Constant folding tidak ada sebagai teknik optimasi bernama
Gap sedangBelum Ada

Constant folding (evaluasi ekspresi konstanta saat compile-time, misalnya 2+3 → 5) adalah optimasi paling dasar yang disebutkan outline §7.9.2.1 sebagai local optimization. Catatan §11.2.11 punya beberapa teknik optimasi tetapi tidak menyebut constant folding. Ini akan mudah muncul sebagai soal "identifikasi optimasi apa yang diterapkan".

§5 RDP — Algoritma general left recursion tidak eksplisit
MinorSebagian

Komentar 9.3 menyebutkan prinsip eliminasi rekursi kiri tidak langsung ("untuk setiap Ai, ganti produksi Ai→Ajγ dengan j<i"). Namun tidak ada algoritma formal lengkap atau contoh konkret dengan dua nonterminal yang saling berulang. Outline menyebutkan ini sebagai poin terpisah. Untuk UAS, soal rekursi kiri tidak langsung jarang tetapi mungkin muncul.

§6 LL(1) — Syarat formal tiga kondisi LL(1) tidak ditulis eksplisit
MinorSebagian

Catatan §10.2.6 mendiskusikan konflik, tetapi tidak merumuskan tiga syarat formal Dragon Book: (1) FIRST(α) ∩ FIRST(β) = ∅; (2) paling banyak satu alternatif nullable; (3) jika ada nullable, FIRST alternatif lain ∩ FOLLOW(A) = ∅. Ketiganya sering muncul sebagai soal "buktikan/tunjukkan bahwa grammar ini LL(1)" dengan langkah formal.

4. Evaluasi struktur dan alur catatan

Secara umum struktur catatan mengikuti outline dengan baik: urutan 8 topik sesuai, tiap section punya sub-section "Outline Fundamental Konsep Materi" → "Penjelasan Konsep" → "Algoritma dan Rumus Penting" yang konsisten dan sistematis.

Beberapa anomali perlu diperhatikan:

Compiler section menjadi "catch-all" yang tidak seimbang. Section Compiler (§8) memuat pembahasan runtime environment, data-flow analysis, live variables — topik yang di outline diletakkan sebagai subbagian di bawah Compiler, tetapi dalam catatan diberi kedalaman setara dengan section utama. Ini membuat Section Compiler menjadi 24 subseksi, jauh lebih panjang dari section lain. Sebaliknya, Code Generation subsection di Compiler sangat tipis (2 subseksi) dibandingkan kedalaman yang seharusnya. Ada ketidakseimbangan vertikal: analisis program (data-flow, live variables) overrepresented; code generation underrepresented.

Error handling tersebar dan tidak memiliki "rumah" di Compiler. Pembaca yang belajar Compiler section akan melewati 24 subseksi tanpa mendapat gambaran bahwa error handling adalah komponen pipeline. Baru di LL(1) section (§10) pembaca menemukan penjelasan yang relevan. Ini berlawanan dengan urutan pipeline yang logis: error handling seharusnya diperkenalkan di Compiler (sebagai konsep), lalu detail implementasinya ada di LL(1).

Postfix/IR dalam Compiler section tidak tersampaikan. Outline §4.9 memasukkan "Intermediate Code dalam Pipeline Compiler" sebagai subbagian eksplisit yang mencakup postfix, 3AC, quadruple/triple sebagai overview pipeline. Catatan tidak punya ini karena konten IR sudah penuh di Section 11. Akibatnya pembaca yang hanya membaca Section Compiler tidak mendapat peta posisi IR.

Transisi antarbagian baik dan konsisten. Setiap section diawali paragraf pengantar yang menjelaskan posisi materi dan kaitan dengan section lain (misalnya PDA→CFL, CYK→decidability, Compiler→parsing sections). Ini aspek yang kuat dari catatan.

Rekomendasi perbaikan struktur: (1) Di awal Compiler section, tambahkan diagram pipeline satu halaman yang menunjukkan posisi semua komponen termasuk error handler dan IR; (2) Pindahkan pengantar postfix ke dalam overview Compiler section §8 (bukan hanya di IR section §11); (3) Tambahkan subbagian Error Handling di Compiler section §8 sebelum pindah ke Lexical Analysis.

8. Kesimpulan akhir

Apakah catatan sudah mencakup seluruh outline? Belum sepenuhnya. Dari ~104 poin outline yang dipetakan, 72 (69%) sudah lengkap, 12 (12%) sebagian, 8 (8%) belum ada, dan 1 terlalu dangkal. Gap paling serius terkonsentrasi di tiga area: (1) Compiler section yang kehilangan Error Handling dan Code Generation detail; (2) Mesin Turing yang kehilangan trace eksekusi konkret dan teorema komplemen; (3) Intermediate Code yang kehilangan postfix sebagai subseksi sistematis.

Apakah catatan sudah cukup lengkap untuk memahami materi? Cukup untuk memahami, tetapi belum cukup untuk mengerjakan seluruh pola soal UAS. Catatan sangat kuat secara konseptual dan definitional, tetapi lemah dalam kesiapan prosedural: trace TM, postfix IR, peephole/graph coloring di code generation, dan error recovery Compiler adalah gap yang langsung berdampak pada kemampuan mengerjakan soal.

Bagian yang paling kuat: LL(1) Parser (§10) adalah section terlengkap dan paling siap-ujian dari seluruh catatan. FIRST/FOLLOW, tabel parsing, trace parsing, error recovery, dan synch entries semua tersedia dengan baik. PDA (§5) dan CYK (§6) juga sangat kuat dengan rumus formal, konstruksi lengkap, dan komentar rawan pemahaman yang efektif.

Bagian yang paling lemah: Compiler section Code Generation adalah titik paling kritis. Section ini menjadi "kurang seimbang" dengan data-flow analysis yang sangat dalam tetapi code generation yang sangat tipis. Setelah itu, Mesin Turing yang kehilangan trace eksekusi dan postfix IR yang tidak punya subseksi sendiri.

Prioritas revisi paling penting: Berdasarkan analisis dan relevansi soal UAS, urutan prioritas adalah: (1) trace TM; (2) postfix IR subseksi; (3) error handling Compiler; (4) code generation teknik lanjutan; (5) teorema komplemen RE; (6) kompleksitas CNF; (7) constant folding + CSE.

Perlu Revisi Sedang

Catatan sudah melampaui rata-rata catatan mahasiswa dalam hal kedalaman dan formalitas. Struktur tiga-bagian per section (outline fundamental, penjelasan, algoritma) dan penggunaan komentar "titik rawan" adalah kekuatan unik yang membuat catatan ini lebih dari sekadar ringkasan. Namun, beberapa pola soal UAS yang paling umum — trace TM, evaluasi postfix, code generation techniques — tidak tercakup. Revisi selama 4–6 jam pada 7 area di atas akan membawa catatan ini ke level sangat lengkap. Tanpa revisi, catatan ini layak untuk soal konseptual dan definitional, tetapi berisiko pada soal prosedural/aplikatif.
